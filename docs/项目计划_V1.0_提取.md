多 Agent 软件研发工作室
项目开发流程与 MVP 实施计划
产品定位：像管理一家软件公司一样，组织 AI Agent 完成真实的软件交付
版本：V1.0  |  日期：2026 年 10 月 16 日
# 一、项目概述
本项目计划开发一个面向软件开发任务的桌面 App。用户用自然语言描述想做的软件；主 Agent（项目主管）负责澄清需求、拆解任务、选择模型与 Agent、协调依赖、管理变更并审核交付；多个专业 Agent 分别承担产品分析、UI/UX、前端、后端、测试、代码审查和文档等工作。最终交付物必须来自真实项目文件与实际执行的验证流程，而不是只生成一段看起来完整的回答。
核心原则：主管审核是流程控制点；测试结论必须有日志和可复现证据；未通过门禁时不得标记为可交付；用户可以在开发过程中提出新想法，系统应记录变更、评估影响并重新安排任务。
# 二、产品目标与边界
## 2.1 第一阶段目标
用户能创建项目、提交需求，并看到主管生成的需求说明、任务拆分和执行计划。
主管能根据任务类型、可用能力、成本预算和上下文要求，路由到不同模型/API。
专业 Agent 在隔离的工作区中执行任务，产出代码、设计稿、测试或文档，并报告文件变更与结果。
用户可以在执行中提出需求变更；主管先评估影响，再更新任务图和版本记录。
自动测试、集成测试、代码审查和主管验收形成明确门禁；失败时进入修复循环或请求用户决策。
交付包含项目文件、运行说明、测试报告、已知限制和版本信息。
## 2.2 MVP 暂不承诺
不承诺一次提示词即可生成任何规模、任何技术栈且完全无缺陷的软件。
不在第一版就支持所有模型供应商、所有操作系统、云端协作和复杂团队权限。
不把 Agent 自报的“测试通过”当作证据；必须由测试运行器实际执行并保存结果。
不允许 Agent 在未经授权的情况下访问用户全部文件、读取密钥、执行高风险命令或向外部发布软件。
# 三、UI 方向：参考 Pixel Agents 的可视化办公室
参考项目：Pixel Agents（GitHub）。其核心体验是把 Agent 显示为像素风办公室中的角色，通过角色动作、状态气泡和办公室布局，让用户直观看到多个 Agent 的活动。本项目可以借鉴“多 Agent 状态可视化、角色可点击、任务状态直观呈现”的交互思路，但应自行设计角色、图块、布局、动画、图标和品牌，不直接复制其专有视觉资产或造成官方关联的误认。
参考链接：https://github.com/pixel-agents-hq/pixel-agents

区域 | 显示内容 | 用户操作

中央像素办公室 | 主管、产品经理、设计师、开发、测试、审查等角色及状态 | 点击角色查看任务、模型、日志；发送指令或请求其解释

右侧详情面板 | 当前任务、文件变更、测试结果、风险和待用户决策项 | 审查差异、批准/退回、追加意见
底部需求输入区 | 用户的新需求、变更和补充说明 | 提交变更、附加文件、选择预算与自动化等级

[TABLE]
状态 | UI 表现建议 | 状态依据

运行测试 | 在测试台工作 | 测试进程已启动

阻塞/需要用户 | 醒目的提示气泡 | 缺少权限、信息或决策

# 四、组织结构与 Agent 职责
[TABLE]
角色 | 主要职责 | 权限与产出
主 Agent / 项目主管 | 理解目标、澄清需求、拆任务、分派、处理变更、审查、决定是否交付 | 维护项目计划和决策记录；不能伪造测试结果
产品分析 Agent | 整理用户故事、验收标准、边界条件 | 需求规格与验收清单
架构 Agent | 选择技术方案、模块边界、接口契约 | 架构说明、依赖图、技术决策记录
UI/UX Agent | 页面结构、交互流程、视觉规范 | 线框稿/组件规范/可运行 UI 代码
前端 Agent | 实现页面、状态管理和前端测试 | 代码提交与前端测试结果
后端 Agent | API、数据模型、业务逻辑、权限 | 代码提交、接口说明和测试
测试 Agent | 单元、集成、端到端、回归测试 | 测试脚本、真实执行日志、缺陷清单
代码审查 Agent | 检查安全性、可维护性、差异和规范 | 审查意见与阻断级问题
文档/交付 Agent | 整理运行说明、变更日志、交付清单 | README、安装/运行指南、交付包
[/TABLE]
重要设计：主管负责决策与把关，但不应成为所有代码的单点执行者。各 Agent 通过明确的输入/输出契约协作；主管审核的是需求、任务计划、合并结果和交付门禁。对高风险操作仍需用户确认。
# 五、端到端研发流程
## 阶段 0：项目初始化
用户创建项目、选择目标平台/技术栈/预算/本地或云端执行方式。系统建立独立工作区、版本库和项目配置。
产物：项目配置；门禁：工作区路径与权限确认。
## 阶段 1：需求接单与澄清
主管把自然语言需求转为结构化需求；识别缺失信息、约束、风险与成功标准。必要时先向用户提问。
产物：需求规格 v0.1、验收标准、假设清单；门禁：用户确认关键需求。
## 阶段 2：方案与任务拆分
产品/架构 Agent 提供方案，主管拆为有依赖关系的任务，指定负责人、输入、输出、模型策略和完成定义。
产物：任务图、技术决策记录、测试策略；门禁：主管审核计划，必要时用户批准。
## 阶段 3：设计与实现
UI、前端、后端等 Agent 在独立分支或隔离工作区中工作；通过接口契约减少互相覆盖。
产物：代码/设计/接口；门禁：格式检查、类型检查、静态检查和任务级自测。
## 阶段 4：集成与持续验证
集成 Agent 合并通过审查的变更，解决依赖冲突；CI 运行构建、单元测试、集成测试和必要的端到端测试。
产物：集成构建与测试报告；门禁：关键测试通过，失败项有明确状态。
## 阶段 5：独立测试与代码审查
测试 Agent 从验收标准出发验证；审查 Agent 检查安全、错误处理、性能风险和代码质量。
产物：缺陷列表、测试日志、审查报告；门禁：阻断级问题清零或经授权明确接受风险。
## 阶段 6：主管验收
主管对照需求、文件变更、测试证据和已知限制逐项验收；不通过则退回具体任务并重新测试。
产物：验收清单与决策记录；门禁：所有强制项通过。
## 阶段 7：交付
生成版本化交付包，包括源代码、安装/运行指南、测试报告、变更日志和已知限制。
产物：可复现交付包；门禁：交付清单完整、版本号固定、无未披露阻断项。
## 阶段 8：变更与迭代
用户随时提交新想法。主管记录变更，评估影响范围、成本和回归风险，更新任务图和版本；必要时暂停相关任务。
产物：变更请求、影响分析、更新计划；门禁：涉及范围/成本明显变化时由用户确认。
# 六、需求变更机制
所有新想法先创建 Change Request，不直接在后台静默覆盖当前任务。
主管判断变更是澄清、低影响修改，还是影响架构/数据结构/API/验收标准的重大变更。
生成影响分析：涉及哪些任务、文件、测试、时间/Token 预算与已完成工作。
为变更创建新需求版本；保留旧版本与决策记录，避免需求历史丢失。
暂停可能与新需求冲突的任务；重新排序任务依赖并通知相关 Agent。
任何已通过的测试，只对其对应代码版本有效；代码变化后应按影响范围重新执行测试。
# 七、模型路由与混合 API 设计
主 Agent 不应把模型名称写死在业务代码里。建议建立统一 Model Gateway，将不同供应商的 API 适配成统一接口，并通过配置管理模型能力、成本、延迟、上下文长度、工具调用能力和可用状态。
[TABLE]
任务类型 | 路由依据 | 策略建议
需求分析/任务规划 | 长上下文、结构化输出、推理稳定性 | 优先使用规划能力强的模型；输出 JSON Schema 校验
UI 方案/前端 | 视觉理解、组件实现、前端调试能力 | 优先派给前端/UI能力合适的模型；必须本地构建验证
后端/复杂代码 | 代码生成、工具使用、上下文和仓库理解 | 选代码能力强的模型；在独立分支执行
测试生成/缺陷定位 | 测试设计、日志分析、反例能力 | 与开发 Agent 尽量分离，减少自我验证偏差
文档/简单任务 | 成本、速度、格式遵循 | 使用成本较低的模型，主管统一检查
[/TABLE]
统一接口至少记录：供应商、模型 ID、请求 ID、耗时、Token/费用（若可获取）、重试次数、错误信息。
对模型不可用设置超时、有限重试、备用路由与明确失败状态；不能无限重试。
API 密钥应保存在系统安全存储或环境配置中，界面默认脱敏，不写入项目日志和交付包。
通过适配器隔离供应商差异；新增模型时原则上新增 Provider Adapter，而不是重写调度核心。
# 八、建议的技术架构
[TABLE]
层 | 职责 | MVP 可选方案（待验证）
桌面/UI 层 | 项目面板、像素办公室、任务看板、日志、审批界面 | Electron + React + TypeScript；Canvas 2D 或 CSS/SVG 做原创像素场景
应用服务层 | 项目、需求版本、任务状态、审批和交付流程 | Node.js + TypeScript；模块化服务
Agent Orchestrator | 任务图、依赖调度、暂停/恢复、重试、审批门禁 | 先用显式状态机/工作流，不一开始就做完全自治
Model Gateway | 多供应商适配、路由、预算、重试和观测 | 统一 Provider 接口 + 配置化路由
工具执行层 | 文件读写、命令执行、Git、构建和测试 | 隔离工作区、命令白名单、超时与权限审批
项目数据层 | 需求版本、事件日志、任务、审批、测试结果 | SQLite 起步；文件与 Git 管理源代码
验证层 | lint、类型检查、单元/集成/E2E、安全检查 | 按项目模板运行；结果可追溯
[/TABLE]
技术选型是初步建议，不是已经验证的结论。应先做一个小型技术验证，重点检查：桌面 UI 与后台事件同步、多 Agent 任务状态恢复、模型适配、隔离执行和测试报告保存。
# 九、分阶段开发计划
[TABLE]
阶段 | 目标 | 主要工作 | 完成标准
P0：产品定义 | 明确边界和验收标准 | 用户画像、典型用例、需求规格、威胁模型、界面草图 | 核心流程与不做事项经确认
P1：交互原型 | 先验证可理解性 | 像素办公室静态原型、Agent 详情、任务看板、需求输入、审批面板 | 用户能看懂状态、阻塞和下一步动作
P2：单 Agent 闭环 | 验证最小开发链路 | 项目创建、需求解析、生成文件、运行测试、展示日志 | 能完成一个小型示例项目并可复现
P3：主管 + 2 个专业 Agent | 验证协作机制 | 主管规划、开发 Agent、测试/审查 Agent、任务状态机 | 任务可分配、失败可退回、主管能阻止不合格交付
P4：多模型路由 | 验证模型可替换 | Model Gateway、能力标签、成本统计、超时/重试/降级 | 切换模型无需改业务流程，失败状态可解释
P5：需求变更 | 验证真实迭代 | 变更单、影响分析、版本化计划、回归测试 | 开发中变更后旧计划不被静默覆盖
P6：质量门禁 | 建立交付可信度 | 单元/集成/E2E、代码审查、测试报告、打包流程 | 门禁失败时不能生成“已验收”状态
P7：封闭试用 | 收集真实使用反馈 | 选择少量低风险项目、记录失败与成本、修复高优先级问题 | 达到预设成功指标后再考虑公开发布
[/TABLE]
# 十、MVP 验收指标
[TABLE]
指标 | 建议测量方式 | 第一轮目标（可调整）
任务追踪完整度 | 所有任务是否有状态、负责人、输入/输出和事件记录 | 核心任务 100% 可追踪
测试真实性 | 测试结果是否来自实际进程，是否保存命令、退出码、摘要 | 不得以模型自述替代测试结果
交付门禁 | 故意制造测试失败，检查是否仍可交付 | 阻断测试失败时 100% 阻止验收
需求变更可追溯 | 提交变更后检查版本、影响分析、关联任务 | 每次变更均留有记录
失败恢复 | 模拟 API 超时、Agent 崩溃、测试失败 | 状态不丢失；能重试、暂停或明确报错
交付可复现 | 在干净环境按文档重新安装/运行 | 至少完成一次独立复现
成本可观测 | 记录模型请求、用量和失败重试 | 可按项目汇总已知成本；无法获取的数据明确标注
[/TABLE]
不要一开始用“生成成功率 100%”作为目标。更有价值的指标是：失败是否可见、能否定位、能否阻止错误交付、以及人工介入次数和单位任务成本是否随迭代下降。
# 十一、关键风险与控制措施
[TABLE]
风险 | 可能后果 | 控制措施
Agent 互相覆盖代码 | 集成冲突、功能回退 | 独立分支/工作区、明确文件所有权、集成前审查
主管错误拆解任务 | 遗漏需求、重复工作 | 验收标准先行、计划审批、任务输出契约
模型虚报完成 | 假通过、交付不可运行 | 所有关键结果由工具运行器核验并保存证据
测试不充分 | 隐藏缺陷 | 按风险设计测试矩阵；记录未覆盖范围和已知限制
API 费用失控 | 项目成本不可控 | 预算上限、任务预算、用量监控、人工确认超预算
密钥/代码泄露 | 数据安全风险 | 密钥脱敏、最小权限、明确数据发送范围、可配置本地/远程处理
不安全命令或文件操作 | 数据丢失或系统风险 | 沙箱、白名单、超时、备份、危险操作二次确认
像素办公室误导用户 | 动画与实际任务不一致 | UI 状态只由后端事件驱动，显示更新时间与真实阻塞原因
过早追求全自治 | 调试复杂、难以验证 | 先做显式状态机和人工审批，再逐步提高自动化程度
[/TABLE]
# 十二、建议的首个演示项目
建议先让系统开发一个规模可控的任务管理 Web App，而不是第一轮就让它开发自身。演示项目应包含登录可先用模拟身份、任务增删改查、简单筛选、持久化存储、基础 UI、单元测试和端到端测试。
演示流程：
用户输入：“做一个任务管理 App，支持新增、完成、筛选任务，界面简洁。”
主管生成需求与验收标准，用户确认。
UI Agent 提供页面结构；前端 Agent 实现界面；后端 Agent 实现数据接口/存储。
测试 Agent 运行测试并发现一个预设缺陷；主管退回对应任务。
修复后重新运行相关测试和回归测试。
用户提出“增加按优先级筛选”；主管生成变更单并调整任务。
系统生成可运行项目、运行指南、测试报告和已知限制。
该演示能验证多 Agent 分工、任务依赖、测试门禁和需求变更，而无需先解决复杂的通用软件自动生成问题。
# 十三、下一步执行清单
确认首发形态：Windows 桌面 App（建议先选一个平台），后续再扩展。
确定首个示例项目与成功标准，不同时支持过多语言/框架。
绘制 4 个关键页面：项目主页、像素办公室、任务详情/差异、审批与交付报告。
设计核心数据结构：Project、RequirementVersion、Task、AgentRun、Artifact、TestRun、Approval、ChangeRequest。
实现任务状态机与事件日志，先用模拟 Agent 跑通流程。
接入一个模型供应商，验证完整闭环后再加入混合 API。
增加真实测试运行器、日志留存和失败门禁。
进行威胁建模与权限设计，再让 Agent 执行文件/命令操作。

# 十四、可直接交给 Trae / 编程 Agent 的项目启动提示词
